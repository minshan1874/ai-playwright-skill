# 测试报告结构

`report.mjs` 生成 `<runDir>/report.md`。这一篇说明每一节的含义，以及呈现给用户时的要求。

---

## 报告结构

| 章节 | 内容 |
| --- | --- |
| 头部信息表 | 被测地址、执行起止、耗时、浏览器、用例数、运行目录 |
| 一、测试结论 | 结论徽标 + 原因列表 + 统计表（通过/失败/不稳定/跳过/未自动化/通过率） |
| 二、用例执行明细 | 按模块分组，逐条列出 ID、标题、优先级、状态、耗时、备注 |
| 三、失败详情 | 每条失败的模块、优先级、位置、重试次数、错误信息、截图与 trace 路径 |
| 四、未自动化用例 | 没有生成自动化用例的清单 |
| 五、未关联到用例的测试 | 没匹配到用例 ID 的测试（通常是临时验证） |
| 六、基础设施错误 | 发生在用例之外、可能导致部分用例没跑的错误 |
| 附件索引 | HTML 报告、JSON 结果、归一化结果、截图/trace 目录 |
| 环境与配置 | baseURL、无头模式、视口、超时、重试、并发、登录态 |
| 附：已确认的测试计划 | 折叠展示，便于追溯本次执行的依据 |

---

## 结论的判定规则

| 结论 | 条件 |
| --- | --- |
| ✅ 通过 | 全部用例通过，没有未自动化、没有跳过、没有 flaky |
| ⚠️ 部分覆盖 | 没有失败，但存在未自动化用例 / 跳过用例 / flaky 用例 |
| ⚠️ 存在不稳定用例 | 没有失败，但有重试后通过的用例 |
| ❌ 未通过 | 有失败用例，或存在基础设施错误 |
| ❌ 未执行 | 一条用例都没跑起来 |

**关键点**：未自动化用例**不计入通过率**。通过率的分母是实际执行的用例数。
这样「跑了 3 条全过」不会伪装成「18 条全过」—— 覆盖缺口单独列在第四节。

---

## 呈现给用户时的要求

`report.md` 已经生成后，**不要只回复「报告已生成，路径 xxx」**。要在对话里给出实质摘要：

```markdown
测试执行完成。

**结论：❌ 未通过** —— 通过率 78.6%（11 通过 / 3 失败 / 0 跳过 / 4 未自动化）

### 失败用例
| 用例ID | 标题 | 失败原因 |
| --- | --- | --- |
| TC-007 | 加入购物车后数量正确 | 期望数量 2，实际 1 |
| TC-012 | 优惠券叠加计算 | 期望 80.00，实际 100.00 |
| TC-015 | 订单列表分页 | 超时：等待行数 10 超过 5s |

### 覆盖缺口（4 条未自动化）
- TC-009 短信验证码登录 —— 需要真实短信通道
- TC-016 支付回调 —— 依赖第三方沙箱
- ……

### 产物
- 报告：`<runDir>/report.md`
- HTML 报告：`<runDir>/playwright-report/index.html`
- 结果 JSON：`<runDir>/results-summary.json`

失败用例的截图和 trace 在 `<runDir>/test-results/`，可以用
`npx playwright show-trace <文件>` 回放。
```

## 汇报失败时的注意事项

### 区分产品缺陷与用例问题

| 迹象 | 更可能是 | 措辞 |
| --- | --- | --- |
| 断言值与实际值有明确业务差异 | 产品缺陷 | 「功能行为与预期不符」 |
| 页面报 JS 异常 / 接口 5xx | 产品缺陷或环境问题 | 「页面出现 JS 错误 / 接口返回 500」 |
| 找不到元素，但截图里元素文案变了 | 用例问题 | 「页面文案已变更，用例需同步」 |
| 偶发超时，重跑通过 | 环境不稳或等待方式不当 | 「存在不稳定因素」 |
| 登录态失效导致全部失败 | 环境问题 | 「登录态过期，需重新登录后重跑」 |

**不要**把用例问题说成产品缺陷，也不要反过来。不确定时如实说「需要进一步确认」。

### 必须主动说明覆盖缺口

未自动化的用例是**测试盲区**。用户看到「测试完成」很容易以为全覆盖了。
必须在摘要里单独列出来，并说明原因和是否需要补测。

### 不要美化结果

- 失败就是失败，不要用「基本通过」「大部分正常」这类模糊措辞。
- flaky 用例要明确标注，不能算作稳定通过。
- 跳过（skip）的用例要说明是谁、为什么跳过的。

---

## 后续动作建议

报告末尾可以给出下一步建议，但要基于事实：

- 有失败 → 建议先确认失败是产品缺陷还是用例问题；给出需要开发/产品确认的具体问题。
- 有未自动化 → 建议评估是否值得投入补测，或改为人工回归。
- 有 flaky → 建议治理（通常是定位器或等待方式问题），给出具体用例。
- 全通过 → 说明覆盖范围与本次未覆盖的部分，避免过度解读。

不要主动承诺「修好之后重跑」这类动作，除非用户明确要求。
