# 测试计划模板

`make-plan.mjs` 生成这个骨架。**下面 5 个部分都必须写实**，不能留 `<!-- -->` 占位符。

---

## 骨架结构

```markdown
# 测试计划

## 1. 测试目标与范围
- 被测地址：<URL>
- 用例总数：N 条，覆盖 M 个模块
- 浏览器：chromium
- 运行目录：<runDir>

<本次要验证的业务目标；明确不测的范围>

## 2. 用例清单
### <模块名>（N 条）
| 用例ID | 标题 | 优先级 | 自动化可行性 |
| --- | --- | --- | --- |

## 3. 执行策略
<登录方式、测试数据准备、执行顺序、需要人工介入的环节>

## 4. 风险与不确定项
<验证码、短信、第三方依赖、动态数据、环境不稳定等>

## 5. 需要用户确认的问题
<必须由用户回答才能继续的问题；没有则写「无」>

状态: 待确认
```

---

## 各部分的写法

### 1. 测试目标与范围

一句话说清这次测什么，然后**明确列出不测什么**。不写「不测什么」的计划无法验收。

```markdown
- 被测地址：https://shop.example.com
- 用例总数：18 条，覆盖 4 个模块
- 浏览器：chromium
- 运行目录：~/.dsh/playwright-e2e/runs/shop-example-com-20250101-120000

本次验证商城前台的核心购买链路：登录、商品搜索、加入购物车、下单。

**不包含**：支付网关真实扣款、优惠券叠加规则、后台管理功能、移动端适配。
```

### 2. 用例清单

逐条标注自动化可行性。这是用户判断「这份计划靠不靠谱」的主要依据。

`自动化可行性` 一列的值：

| 值 | 含义 |
| --- | --- |
| `可自动化` | 常规操作 + 断言，直接写 spec |
| `需登录` | 需要登录态，会在执行前统一登录并复用 |
| `需测试数据` | 依赖特定数据，需说明数据从哪来 |
| `需人工` | 验证码、短信等，执行到该步骤需要人工介入 |
| `无法自动化` | 纯人工判断或依赖外部系统，**不会执行**，报告中列为未自动化 |

```markdown
| 用例ID | 标题 | 优先级 | 自动化可行性 |
| --- | --- | --- | --- |
| TC-001 | 正确账号密码登录成功 | P0 | 可自动化 |
| TC-004 | 搜索关键字返回结果 | P0 | 需测试数据（至少存在 1 个上架商品） |
| TC-009 | 短信验证码登录 | P1 | 无法自动化：需要真实短信通道 |
```

### 3. 执行策略

```markdown
- **登录**：使用测试账号 `qa_bot`，通过 `storageState` 登录一次后全用例复用。
  凭据通过环境变量 `E2E_USERNAME` / `E2E_PASSWORD` 注入。
- **测试数据**：购物车相关用例执行前会清空购物车；下单用例使用测试商品
  `SKU-TEST-001`，不会产生真实订单。
- **执行顺序**：各用例相互独立，可任意顺序执行，并发度 1。
- **浏览器可见性**：默认有头，执行时会弹出浏览器窗口，你可以看到全过程；
  嫌快可以加 `--slow-mo 500` 放慢；不想弹窗就用 `--headless`。
- **人工介入**：无。
- **失败处理**：失败用例保留截图与 trace，不做自动重试以外的任何补救。
```

### 4. 风险与不确定项

**这一节是计划里最有价值的部分。** 如实写，不要为了显得顺利而省略。

```markdown
- 搜索接口依赖 Elasticsearch，测试环境偶有 5xx，可能出现非产品缺陷的失败。
- 商品价格会随时间变化，涉及金额的断言只校验格式与数量级，不校验具体数值。
- 「下单成功」页面会弹出营销弹窗，需要先关闭；若弹窗文案变更，用例需同步调整。
- 未确认测试环境是否会限流，若触发限流将改为串行并降低频率。
- 文生图任务实测排队约 40s、生成约 90s，已按「提交 30s / 完成 180s」设置异步预算；
  若高峰期更慢，需要调大 asyncTasks.completionTimeout。
```

### 5. 需要用户确认的问题

把「猜错会浪费一整轮执行」的问题放这里。**有疑问就问，不要自己假设。**

```markdown
1. 测试账号 `qa_bot` 是否有下单权限？会不会产生真实订单？
2. 「搜索结果」的排序规则是什么？用例里需要校验排序吗？
3. 环境是否有验证码？如果有，测试环境是否可以关闭？
```

没有疑问时明确写：

```markdown
无。
```

## 展示给用户时的要求

生成计划后，把 `plan.md` 的**完整内容**呈现给用户，并明确请求确认。不要只说
「计划已生成，路径是 xxx」。

推荐措辞：

> 测试计划已生成（`<runDir>/plan.md`），共 18 条用例覆盖 4 个模块。
> 其中 15 条可自动化，1 条需人工介入，2 条无法自动化（短信验证码、真实支付）。
> 有 2 个问题需要你确认：……
>
> 请确认后我再开始执行。如果计划需要调整，直接告诉我改哪里。

用户确认后，用 `confirm-plan.mjs` 打开执行闸门，**不要手工编辑状态行**。

---

## 计划变更

用户要求修改时：

- 小改（补充说明、调整可行性标注）→ 直接编辑 `plan.md`，然后**再次展示并等待确认**。
- 大改（用例增删、范围变化）→ `make-plan.mjs --force` 重新生成骨架，重新填写。

无论哪种，改完后状态行必须是 `待确认`，需要重新确认。
